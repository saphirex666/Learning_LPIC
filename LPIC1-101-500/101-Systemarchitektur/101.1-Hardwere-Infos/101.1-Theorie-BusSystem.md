# Linux Bus-Systeme und GPIO mit Fokus auf I²C  
### LPIC-1/2/3-relevante Übersicht für Administration und Troubleshooting

## 1. Grundlogik: Wie Linux Hardware immer handhabt (LPIC-Core)

Linux trennt Hardware sauber in Schichten:

1. **Hardware / Bus** (I²C, SPI, UART, PCI, USB, …)  
2. **Kernel-Treiber** (Module oder built-in)  
3. **Geräteobjekte im Kernel** → sichtbar in `/sys` (sysfs)  
4. **Device Nodes** in `/dev` (Character/Block Devices)  
5. **Userland-Tools** (i2c-tools, libgpiod, udev, systemd, etc.)

**LPIC-Merksatz** (Exam-relevant ⭐):

- `/sys` = „Kernel sieht und beschreibt Geräte“  
- `/dev` = „Userland greift zu“  
- `lsmod` / `modprobe` / `dmesg` / `journalctl` = „Treiber & Events verstehen“

## 2. Wichtigste Bus-Systeme in Linux

### Interne / schnelle Busse
| Bus      | Typische Geräte                     | Wichtige Tools                              |
|----------|-------------------------------------|---------------------------------------------|
| PCI/PCIe | Grafikkarten, NVMe, Netzwerkkarten   | `lspci -nnk`, `lsmod`, `modinfo`, `dmesg`   |
| USB      | Sticks, WLAN-Adapter, Kameras       | `lsusb -t`, `lsusb -v`, `udevadm monitor`   |

### Board- und Embedded-nahe Busse
| Bus     | Merkmale                                          | Typische Anwendung               |
|---------|---------------------------------------------------|----------------------------------|
| I²C     | 2 Leitungen (SDA/SCL), Adressierung               | Sensoren, RTC, OLED-Displays     |
| SPI     | Schneller, 4+ Leitungen (MOSI/MISO/SCLK/CS)       | Displays, ADCs                   |
| UART    | Seriell, Punkt-zu-Punkt                           | Console, GPS, Modems             |
| 1-Wire  | Sehr simpel, eine Datenleitung                    | Temperatursensoren (DS18B20)     |
| CAN     | Robust, differenziell                             | Automotive, Industrie            |

**LPIC-relevant**: Jeder Bus = Kernel-Subsystem + Treiber + `/sys` + `/dev` + udev-Regeln.

## 3. I²C in Linux – Das wirklich Wichtige

### 3.1 Grundprinzip (praktisch)
- Mehrere Geräte an einem Bus → jede hat eine **7-Bit-Adresse** (10-Bit selten)  
- **Pull-Up-Widerstände** sind hardwareseitig Pflicht!  
- Typische Geschwindigkeiten: 100 kHz / 400 kHz  
- Häufige Fehler:
  - Falsche Adresse / Konflikt
  - Fehlende oder zu schwache Pull-Ups
  - Zu lange Leitungen / Störungen
  - Gerät „hängt“ den Bus (SDA stuck low, Clock stretching)

### 3.2 Linux-Sicht
- Adapter erscheinen als `/dev/i2c-0`, `/dev/i2c-1`, …  
- Sysfs-Struktur: `/sys/bus/i2c/` (Devices, Drivers, Adapter)

### 3.3 Standard-Tooling (i2c-tools) – Exam-relevant ⭐⭐
| Befehl                              | Funktion                                          |
|-------------------------------------|---------------------------------------------------|
| `i2cdetect -l`                      | Listet verfügbare I²C-Adapter                     |
| `i2cdetect -y <bus>`                | Scannt Bus nach Geräteadressen                    |
| `i2cget -y <bus> <addr> <reg>`      | Liest ein Register                                |
| `i2cset -y <bus> <addr> <reg> <value>` | Schreibt ein Register                          |
| `i2cdump -y <bus> <addr>`           | Dump aller Register (Vorsicht: kann stören)       |

**LPIC-Punkt**: Verifikation von Hardware mit Tools + Rechte/Zugriff regeln (Gruppen, udev).

### 3.4 Treiber-Bindung
- Viele I²C-Geräte brauchen einen echten Kernel-Treiber → dann erscheinen sie z. B. unter `/sys/class/hwmon`, `/dev/input`, etc.  
- Wichtige Befehle: `lsmod`, `modprobe`, `modinfo`, `dmesg -T`, `journalctl -k`

## 4. GPIO in Linux – Moderne Best Practice

### 4.1 Zwei Welten
| Ansatz              | Pfad                      | Status            | Empfehlung                  |
|---------------------|---------------------------|-------------------|-----------------------------|
| Alt (sysfs)         | `/sys/class/gpio`         | **Deprecated**    | Nur noch in alten Tutorials |
| Neu (char device)   | `/dev/gpiochip0`, …       | Aktueller Standard| **Verwenden!**              |

### 4.2 libgpiod-Kommandos (Exam-relevant ⭐⭐)
| Befehl                              | Funktion                                          |
|-------------------------------------|---------------------------------------------------|
| `gpiodetect`                        | Listet gpiochips                                  |
| `gpioinfo`                          | Zeigt Lines, Namen, Status, Consumer              |
| `gpioset gpiochip0 17=1`            | Setzt Pin high                                    |
| `gpioget gpiochip0 17`              | Liest Pin                                         |
| `gpiomon gpiochip0 17`              | Überwacht Flanken-Events                          |

**Kernkonzepte**:
- Direction (in/out)
- Pull-up/down (meist SoC-abhängig)
- Edge-Events
- Exclusive Access (Consumer)

### 4.3 Rechte & Permissions (wichtig für LPIC!)
- Zugriff über Dateirechte + Gruppen (`i2c`, `gpio`, …)  
- Sauberer Weg: **udev-Regeln**

## 5. udev – Zentral für Busse und GPIO (LPIC-Gold ⭐⭐⭐)
udev steuert:
- Erzeugung von Device-Nodes (Name, Permissions)
- Symlinks
- Aktionen beim Hotplug/Erkennen

**Must-know**:

```bash
udevadm info -a -n /dev/i2c-1      # Alle Attribute eines Devices
udevadm monitor --udev --kernel   # Live-Monitoring
```

# Linux Bus-Systeme (I²C / GPIO) – Debug, LPIC-Relevanz & Cheatsheet

## 6. Standard-Debug-Workflow

### 1) Hardware gesehen?
- **I²C**
  - `i2cdetect -l`
  - `i2cdetect -y <bus>`
- **GPIO**
  - `gpiodetect`
  - `gpioinfo`

### 2) Treiber geladen und gebunden?
- `lsmod`
- `modinfo <modul>`
- `dmesg -T | tail -200`

### 3) Einträge in `/sys`?
- `/sys/bus/i2c/devices/`
- `/sys/class/hwmon/`

### 4) Zugriff/Rechte OK?
- `ls -l /dev/i2c-* /dev/gpiochip*`
- Gruppen- und **udev**-Prüfung


## 7. LPIC-Relevanz nach Level

| Level  | Fokus |
|--------|-------|
| **LPIC-1** | Device Files, Major/Minor, Kernel-Module, `/proc` & `/sys`, Permissions, `dmesg`/`journalctl` |
