# Linux Kernel-Module & Treiber – Tiefgehende Erklärung

Dieses Dokument erklärt **wie Kernel-Module intern funktionieren**, **wie Treiber an Hardware gebunden werden** und **was beim Laden wirklich passiert**.

---

## 1. Kernel Space vs. User Space (Fundament)

### 1.1 Zwei strikt getrennte Welten

| Bereich       | Rechte                 | Zweck                              |
|---------------|------------------------|------------------------------------|
| **User Space**  | eingeschränkt          | Anwendungen, Shells, Services      |
| **Kernel Space**| volle Hardwarekontrolle| Kernel, Treiber, Module            |

👉 **Kein User-Programm darf direkt auf Hardware zugreifen.**  
👉 **Alles läuft über den Kernel.**  
Systemaufrufe (Syscalls) sind die **einzige Brücke** zwischen beiden Welten.

---

## 2. Was ein Kernel-Modul technisch ist

Ein Kernel-Modul ist:

- **kompilierter Maschinencode**
- **gegen exakt eine Kernel-Version gebaut**
- **dynamisch ladbar**

**Dateiformat:**  
`.ko` (kernel object) = ELF-Binary + `.modinfo`-Sektion

### 2.1 Warum Module kernelversionsabhängig sind

Der Kernel exportiert **Symbole** (Funktionen, Variablen). Module werden **zur Laufzeit** dagegen gelinkt.

➡️ Ändert sich der Kernel → ändern sich Symbole → Modul passt möglicherweise nicht mehr.

**Praktisch:**

```bash
uname -r                                # Aktuelle Kernel-Version
ls /lib/modules/$(uname -r)/            # Nur Module für genau diese Version
```



## 3.Lebenszyklus eines Kernel-Mod

### 3.1 Laden (modprobe)

```bash
modprobe e1000e
```   

**Intern:**  
  1.Prüfung von Abhängigkeiten  
  2.Laden in den RAM  
  3.Aufruf der init()-Funktion  
  4.Registrierung beim Subsystem  
  4.Gerät aktiv  

### 3.2 Entfernen (modprobe -r)

```bash
modprobe -r e1000e
```
**Intern:**  

  1. Prüfung auf Nutzung (Referenzzähler)  
  2. Aufruf der exit()-Funktion  
  3. Freigabe von Ressourcen  
  4. Entladen aus dem Kernel-Space  

⚠️ Bei Nutzung → Blockiert

  
## 4. Wie ein Treiber an Hardware gebunden wird  


### 4.1 PCI-Geräte als Beispiel  

**Jedes PCI-/PCIe-Gerät hat:**  
  Vendor ID  
  Device ID (z. B. 8086:15f3)  

### 4.2 Matching-Prozess
Beim Boot oder Hotplug:  

Kernel erkennt Hardware  
Liest IDs aus dem Konfigurationsraum  
Vergleicht mit ID-Tabellen der Module  
Bindet den passenden Treiber  

👉 Deterministisch – immer derselbe Treiber bei gleicher Konstellation.


### 4.3 Sichtbar machen

Bashlspci -k                    # Zeigt gebundenen Treiber
ls -l /sys/bus/pci/devices/0000:03:00.0/driver   # Symlink zum Treiber

## 5. Warum Treiber im Kernel Space laufen müssen

Treiber müssen:

Interrupts verarbeiten
DMA konfigurieren und steuern
Direkt in Hardware-Register schreiben
Speicher physisch adressieren

👉 All das ist nur im Kernel Space (Ring 0) erlaubt.
Konsequenzen:

Treiberfehler → Kernel Panic (Systemabsturz)
Keine Isolation wie bei User-Programmen


## 6. Open Source vs. Binäre Treiber
### 6.1 Open-Source-Treiber (im Kernel integriert)
Vorteile:

Automatische Updates mit dem Kernel
Besser debugbar
Gemeinschaftlich auditiert → sicherer
Stabile Integration

Nachteil:

Manchmal langsamere Adaption neuer Hardware-Features

### 6.2 Proprietäre/binäre Treiber (z. B. NVIDIA)
Technisch:

Kernel-Modul + User-Space-Bibliotheken
Oft über DKMS nachgebaut bei Kernel-Updates

Risiken:

Kernel-Update → Treiber kaputt (bis Neu-Build)
Kein Quellcode → kein Community-Audit
Starke Abhängigkeit vom Hersteller


## 7. udev – das Bindeglied zur Praxis
udev (heute Teil von systemd):

Reagiert auf Hardware-Ereignisse (uevents)
Lädt automatisch passende Module
Erzeugt Device-Nodes im /dev

Ablauf:
textHardware → Kernel → uevent → udev → modprobe → Device-Node (/dev/...)
Beispiele:
text/dev/nvme0n1
/dev/eth0
/dev/snd/*

## 8. Kernel-Module & Sicherheit
### 8.1 Warum Module hochkritisch sind

Laufen mit vollen Ring-0-Rechten
Kein Memory-Sandboxing
Können das gesamte System kompromittieren

Schutzmaßnahmen:

Secure Boot: Signiert Module prüfen
Unsigned Modules können blockiert werden

### 8.2 Blacklisting von Modulen
Datei: /etc/modprobe.d/blacklist.conf
Beispiel:
textblacklist nouveau
Nützlich für:

Proprietäre Treiber-Installation
VFIO-Passthrough
Sicherheits-Hardening


## 9. Kernel-Module im Kontext von VFIO & Passthrough
Beim PCI-Passthrough (z. B. GPU an VM):

Gerät wird erkannt
Standardtreiber wird unterdrückt (blacklist oder unbind)
Gerät wird manuell an vfio-pci gebunden
VM übernimmt direkte Kontrolle

Ergebnis in lspci -k:
textKernel driver in use: vfio-pci
👉 Der Originaltreiber darf nicht greifen.

## 10. Mentales Modell
Der Kernel ist der Dirigent
Kernel-Module sind seine Instrumente
Treiber sind spezialisierte Instrumente für exakt ein Gerät (oder eine Geräteklasse)

## 11. Merksätze (Prüfung + Praxis)

Kernel-Module erweitern den Kernel zur Laufzeit
Treiber sind Kernel-Module mit Hardware-Binding
Der Kernel entscheidet, welcher Treiber welches Gerät bekommt
Falscher oder fehlerhafter Treiber → Instabilität / Panics
Passthrough = bewusste Entkopplung vom Host-Treiber


## 12. Fazit

Kernel-Module sind kein harmloses Plugin-System – sie werden vollwertiger Teil des Kernels
Treiber sind der kritischste Code im gesamten System
Linux funktioniert so zuverlässig, weil die meisten Treiber fest integriert und open source sind
Tiefes Verständnis von Modulen und Treibern = Debugging-Superkraft und Grundlage für Virtualisierung, Server-Betrieb und Hardening
